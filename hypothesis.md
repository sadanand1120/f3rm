# Active Hypotheses

- 2026-03-18: Replace wave-based CLIP scheduling with dynamic worker dispatch. The official `measure` baseline still runs extraction in fixed waves with `extract.num_workers=8`, and the logs show repeated waits for whole waves to drain before the next group starts. GPU overlap is valid, but `extract.batch_compute_s=341.42798` leaves enough room that smoother dispatch may still win.
- 2026-03-18: Cut CLIP startup cost by parallelizing worker construction, but do not fan out all workers at once. A naive full parallel init already failed an `exp17` smoke gate on the default 8-worker extractor path: `extract.worker_init_s=24.738966`, which is enough evidence to avoid broad fan-out without tighter scoping. Startup is still a real target, but the next attempt needs tighter scope.
- 2026-03-18: Reduce per-image feature write cost or change the cache layout. The official `measure` baseline spent `extract.per_image_write_s=90.624241`, which is too large to ignore relative to `extract.batch_compute_s=341.42798`.
- 2026-03-18: Reduce training feature-window fetch cost instead of micro-optimizing stacking. On the official `measure` baseline, `train_feature_window_fetch_avg_s=0.6935027241706848` across 10 refreshes, while `train_feature_window_stack_avg_s=0.0015003500739112496` and `Train/feature_lookup_build/total_s=0.002903980202972889` were both tiny.
- 2026-03-18: Batch or overlap H2D feature transfers more aggressively during window refreshes. `exp16` validated this direction: deferring the CUDA stream wait to once per window cut `train_feature_window_fetch_avg_s` from `0.5950055122375488` (`exp13`) to `0.4681392312049866` and set a new best `end_to_end_wall_s=406.3298032800667`. Keep pushing only if the next change preserves the current code simplicity.
- 2026-03-18: Re-baseline against current machine conditions before trusting small wins. `exp21` reran the restored `exp16` path unchanged and landed at `end_to_end_wall_s=438.3688122751191`, with `extract_batch_compute_s=320.553911` and `train_feature_window_fetch_avg_s=0.9371415376663208`, so near-term comparisons should be made against `exp21`, not the earlier `406.33s` low-water mark.
- 2026-03-18: Do not prefetch next feature windows onto the training GPU during active training. `exp17` drove `train_feature_window_fetch_avg_s` down to `0.18565914034843445`, but `train_wall_s` rose to `93.49180433701258` and `peak_train_gpu_mem_mb` jumped to `21886`, so the work was mostly hidden from the narrow metric while still contending with training.
- 2026-03-18: Try a much larger non-pinned CPU feature cache before adding more training-side machinery. The current box still runs with `F3RM_CPU_FEATURE_CACHE_IMAGES=32`, while each cached feature file is only about `57.3 MiB` and the host has ample free RAM, so keeping the full 159-image dataset resident in pageable RAM is a clean untested locality experiment.
- 2026-03-18: Large pageable CPU feature-cache residency is a keep on the current box. `exp22` set `F3RM_CPU_FEATURE_CACHE_IMAGES=159` with `pin_cpu_feature_cache=0` and cut `train_feature_window_fetch_avg_s` from `0.9371415376663208` (`exp21`) to `0.3295115530490875`, bringing `train_wall_s` down to `89.39089179399889` and `end_to_end_wall_s` down to `428.02859957597684`.
- 2026-03-18: Reusing one decoded RGB tensor across CLIP aggregation scales was not enough on its own. `exp20` kept visuals correct, but still landed at `end_to_end_wall_s=431.3933105460601` with `extract_batch_compute_s=310.202209`, so repeated image decode is not the dominant blocker relative to the rest of the extractor path.
- 2026-03-18: Revisit extraction worker count vs. GPU residency. With `CUDA_VISIBLE_DEVICES=6,7`, the current resolver still creates multiple full CLIP workers per GPU, and the official `measure` baseline peaked at `25334 MB` on extraction GPUs before any code changes.
- 2026-03-18: Revisit CLIP startup now that training fetch improved. Even after `exp16`, `extract.worker_init_s=13.620226` is still materially larger than `extract.worker_warmup_s=0.237247`, so parallel worker construction is still the strongest clean extractor-side lever.
- 2026-03-18: If startup is revisited, parallelize CLIP worker construction across devices but not within the same device. The naive full fan-out patch already failed on the 8-worker smoke path, but the current contract only needs two visible GPUs and four workers, so per-device scoped construction is still plausible.
- 2026-03-18: Keep looking for startup-only lazy imports or setup work around extraction and training startup. This is now lower priority than worker init, feature writes, and window fetches, but it is still plausible cleanup work if the primary bottlenecks flatten out.
