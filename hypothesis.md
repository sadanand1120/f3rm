Relative to the prior accepted point (`c95beba`), it cut `wall_time_s` `110.43 -> 108.24`, `train_total_time_s` `96.33 -> 94.54`, `train_iter_time_s` `0.01414 -> 0.01310`, and peak GPU `7822.88 -> 7273.79 MB` while staying clear at `9.40%` max regression.

Simply inflating the train window to `64` images / `600` repeats (`1dcadc6`) stayed clear at `7.02%` but was slower at `110.28s` and raised peak GPU to `13.1 GB`; `51` images / `480` repeats (`70eef32`) slipped into judgment at `11.44%`; and keeping the uint8 train images off GPU entirely (`273c265`) cratered throughput to `887k` rays/sec and `133.88s`. The sweet spot remains `32` images / `300` repeats with train-only uint8 images resident on GPU.

The fair `14080 / 4704 / 294` rerun (`2b2a05f`) improved to `109.64s` but still landed in judgment at `10.25%`, the in-between `14336 / 4629 / 290` point (`b283244`) was faster again at `109.48s` but worse on quality at `11.50%`, `num_nerf_samples_per_ray=19` (`8fa078f`) reached `109.38s` at `10.60%`, and `num_proposal_samples_per_ray=(88,)` (`921d695`) reached `109.30s` at `10.45%`. Caching the auxiliary supervision index tensor and reusing the foreground CE / label path (`32121dd`) kept quality clear (`9.41%`) but landed slightly slower at `110.24s`, so the remaining hot cost is still in the actual rendered/model work rather than that bookkeeping.
- `P0` The biggest code win in this sweep was not another auxiliary-head change; it was specializing sampled-ray generation in [ray_generator.py](/robodata/smodak/repos/f3rm/f3rm/ray_generator.py) for the actual poster-camera regime. Moving sampled coord lookup onto the camera device, flattening the lookup, and then precomputing perspective camera-space ray geometry on the main base cut `wall_time_s` `158.99 -> 123.60`, `train_batch_load_s` `0.00795 -> 0.00180`, and `train_iter_time_s` `0.02040 -> 0.01517` while staying clear (`9.66%`).

Detaching latest metrics without forcing a CPU sync and skipping redundant image transfers reached `158.32s` (`797cfcc`), the flattened coord lookup alone reached a clear `158.14s` (`fa5d6e9`), and combining the loop trims with the precomputed-ray path reached the same `123.60s` speed but slipped into the judgment band (`30e3c85`, `10.84%`). The ray-path rewrite matters more than the trainer bookkeeping tweaks.
- `P0` Once sampled-ray generation stopped dominating, the best schedule moved to fewer, larger optimizer steps at roughly fixed ray budget. `12288 / 5400 / 360` reached `117.61s` but only in judgment (`13.84%`). - `P0` More invasive feature-head cuts still have room, but TCNN kernel constraints matter. Setting `feat_num_layers=1` crashes on the current `tcnn` path because `FullyFusedMLP` requires a hidden layer, and shrinking `feat_hidden_dim 64 -> 48` forces the slower `CutlassMLP` fallback. That width-cut variant still reached `162.14s`, but only in the judgment band (`12.85%`), so future capacity sweeps should stay on fused widths (`32`, `64`, `128`) or switch implementations deliberately.
- `P0` Preserve the baseline eval-image identity when moving `steps_per_eval_image`. `FeaturePipeline._get_deterministic_eval_camera_and_batch()` picks the eval image as `step % num_eval`, so changing the eval-image step can change the measured image and create fake quality deltas. Short-run configs should place the near-end eval-image step at the same modulo-`num_eval` residue as the baseline (`7500 % 11 = 9`) before drawing conclusions from `Eval Image/*` regressions.
- `P0` The fair-eval reruns showed that eval-image residue can hide both false negatives and false positives. Aligning the near-end eval step back to the baseline residue (`step % 11 = 9`) kept the comparisons clean across the `9216`, `9472`, `9984`, `10240`, `10752`, and `11520` schedule families, and it was necessary to separate genuinely strong schedules from residue artifacts.

# Out Of Scope Issues For Human

- Build a repo utility that converts existing `features/foreground_` caches from float one-hot maps to compact uint8 label maps and rewrites any needed metadata, then run it across the scenes you care about. The runtime path already supports compact labels, but the repo does not yet give you a clean one-command migration workflow.
- Decide whether you want to invest in a CLIP-cache format project. The concrete work would be: choose an acceptable compressed representation, add a cache conversion or re-extraction path, and then run a fresh quality sweep to confirm the feature field still trains acceptably. That is a larger offline-data project than this contract pass should take on.
- Improve cold-start performance at the environment level if code-path startup cleanup is exhausted. Concretely: profile Python import startup in the container, trim unnecessary editable-install paths, and simplify the runtime image or environment so `ns-train` reaches the actual training loop faster.
- If you are willing to carry a local Nerfstudio fork, decide that explicitly and provide the policy for it. Then any unavoidable hot-path Nerfstudio changes can be staged under `nerfstudio_changes/` and copied manually, instead of being blocked by the no-site-packages-edit rule.
