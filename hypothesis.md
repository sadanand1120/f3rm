# Active Hypotheses

- `P0` Reduce per-step safety scanning in [f3rm/trainer.py](/robodata/smodak/repos/f3rm/f3rm/trainer.py). The trainer currently walks parameter tensors and optimizer state on every optimizer step even when loss and grads are finite. Move sanitization to a triggered slow path or a much sparser check. Expected gain: lower train-step CPU overhead with no intended quality change.
- `P0` Reduce feature gather overhead in [f3rm/feature_datamanager.py](/robodata/smodak/repos/f3rm/f3rm/feature_datamanager.py). Each batch rebuilds per-camera feature dicts, recomputes `torch.unique(...)`, and stacks tensors separately for CLIP and foreground. Reuse the camera grouping once and avoid duplicate batch assembly. Expected gain: lower `Timing/*/feature_gather` and `Timing/*/feature_populate`.
- `P0` Tune feature cache sizes around the fixed benchmark window in [f3rm/f3rm_config.py](/robodata/smodak/repos/f3rm/f3rm/f3rm_config.py). The measure profile repeatedly trains on 27-image windows and evals on 11 images, while the current cache defaults are much larger. Test whether a train-window-fit GPU cache or a smaller CPU/GPU cache reduces reload churn or memory pressure without hurting throughput.
- `P1` Shrink feature-head compute before touching base Nerfacto. Candidate knobs in [f3rm/f3rm_config.py](/robodata/smodak/repos/f3rm/f3rm/f3rm_config.py): `feat_hidden_dim`, `feat_num_layers`, `foreground_hidden_dim`, `foreground_num_layers`, `feat_num_levels`, and possibly `num_proposal_iterations`. Expected gain: lower `Timing/Train/model_forward`; keep only if final metrics stay in the acceptable quality band.
- `P1` Test whether camera optimization is worth its cost on `poster`. [f3rm/f3rm_config.py](/robodata/smodak/repos/f3rm/f3rm/f3rm_config.py) enables `CameraOptimizerConfig(mode="SO3xR3")`, which adds extra parameters and optimizer work. If this scene is already well-posed, disabling or simplifying camera optimization could be a clean speed win.
- `P1` Remove avoidable eval-side terminal/progress work in [f3rm/pipeline.py](/robodata/smodak/repos/f3rm/f3rm/pipeline.py). The benchmark already does final-only eval, but the pipeline still wraps eval renders in rich progress bars. That does not affect training quality and directly contributes to measured wall time.
- `P1` Cut redundant device and dtype conversions in [f3rm/model.py](/robodata/smodak/repos/f3rm/f3rm/model.py). `batch["feature"]` and `batch["foreground"]` already arrive device-ready from the datamanager, yet metrics and losses re-run `.to(...)` casts each step. Reusing a single fp32 view per batch may shave some overhead.
- `P2` Raise eval ray chunk size if the single GPU has headroom. [f3rm/model.py](/robodata/smodak/repos/f3rm/f3rm/model.py) uses `eval_num_rays_per_chunk=1 << 14`; larger chunks may reduce Python overhead during final eval, but this must be traded against peak memory.
- `P2` Further import cleanup is probably secondary. [f3rm/trainer.py](/robodata/smodak/repos/f3rm/f3rm/trainer.py) already stubs viewer imports for non-viewer runs, and [f3rm/features/extract_features_standalone.py](/robodata/smodak/repos/f3rm/f3rm/features/extract_features_standalone.py) already lazy-imports extractors. Startup overhead should still be measured, but import work should stay lower priority unless it clearly dominates wall time.
- `P2` Avoid per-batch Python container churn in [f3rm/features/utils.py](/robodata/smodak/repos/f3rm/f3rm/features/utils.py) and [f3rm/feature_datamanager.py](/robodata/smodak/repos/f3rm/f3rm/feature_datamanager.py). The current path builds fresh dicts and tensor lists every batch. If timings still point to datamanager overhead after the higher-priority fixes, flatten that path.
