# Active Hypotheses

- `P0` The current speed bar is the accepted `9984`-ray / `6656`-iter / `416`-repeat schedule with `distortion_loss_mult=0.003`, `num_proposal_samples_per_ray=(96,)`, and `num_nerf_samples_per_ray=20`. It cut official `wall_time_s` from `332.51` to `198.45`, raised train throughput to `460k` rays/sec, and stayed in the clear quality band (`4.77%` max regression). The strongest path so far is not a single giant batch jump; it is a shorter schedule that gets its distortion regularization back before trimming proposal and NeRF samples.
- `P0` Coverage-preserving short schedules are viable, but only after re-tuning distortion regularization. The raw `9984` schedule reached `213.04s` with `11.57%` max regression, and the fair `10240` schedule reached `209.16s` but failed at `15.82%`. Raising `distortion_loss_mult` from `0.0025` to `0.0030` rescued the `9984` point down to `216.05s` with only `1.95%` max regression, which created the quality headroom needed for the later sample-count cuts.
- `P0` With `num_proposal_iterations=1`, only the first `num_proposal_samples_per_ray` entry is active in Nerfstudio’s `ProposalNetworkSampler`. Replacing the dead two-entry tuple with `(96,)` on the rescued `9984` schedule yielded `204.53s` at `2.29%` max regression, so further GPU squeezing should focus on the live proposal sample count and the final NeRF sample count, not on unused tuple entries.
- `P0` Any reduced-iteration config must also move the near-end eval thresholds with it. A `10240`-ray / `6480`-iter test showed the training-side throughput win is real, but leaving `steps_per_eval_image=7500` and `steps_per_eval_all_images=7700` above `max_num_iterations` dropped the official final eval block from the summary. Future coverage-preserving shorter runs need a near-end eval schedule that still emits the benchmark’s final metrics.
- `P0` Preserve the baseline eval-image identity when moving `steps_per_eval_image`. `FeaturePipeline._get_deterministic_eval_camera_and_batch()` picks the eval image as `step % num_eval`, so changing the eval-image step can change the measured image and create fake quality deltas. Short-run configs should place the near-end eval-image step at the same modulo-`num_eval` residue as the baseline (`7500 % 11 = 9`) before drawing conclusions from `Eval Image/*` regressions.
- `P0` The fair-eval reruns showed that eval-image residue can hide both false negatives and false positives. Aligning the near-end eval step back to the baseline residue (`step % 11 = 9`) kept the comparisons clean across the `9216`, `9472`, `9984`, and `10240` schedules, and it was necessary to separate the genuinely strong `9984` family from the genuinely weak `9472` and `10240` variants.
- `P0` Split cache-hit training startup from extraction and viewer startup in [feature_datamanager.py](/robodata/smodak/repos/f3rm/f3rm/feature_datamanager.py) and [model.py](/robodata/smodak/repos/f3rm/f3rm/model.py). The benchmarked path only needs cached CLIP/foreground loaders plus tensorboard logging, but training still imports [extract_features_standalone.py](/robodata/smodak/repos/f3rm/f3rm/features/extract_features_standalone.py) and viewer UI helpers at module import time. A lighter cache-loader path or deeper lazy imports could cut `startup_overhead_s` without changing training behavior.
- `P0` Narrow the non-finite safety path in [trainer.py](/robodata/smodak/repos/f3rm/f3rm/trainer.py). The current hot path still materializes optimizer-group parameter lists, unscales grads, and scans every gradient tensor every optimizer step. A coarse removal is risky because the trainer is explicitly guarding non-finite states, but a triggered slow path keyed off non-finite loss or scaler behavior may keep stability while shaving train-step CPU overhead.
- `P1` Specialize the foreground fast path for the now-common uint8 label cache in [feature_datamanager.py](/robodata/smodak/repos/f3rm/f3rm/feature_datamanager.py) and [model.py](/robodata/smodak/repos/f3rm/f3rm/model.py). The runtime already supports uint8 labels, but metrics/loss code still keeps the more general one-hot path. A direct label path could remove small but repeated conversion overhead.
- `P1` Re-open train batch preparation before touching more model knobs. The code path in [feature_datamanager.py](/robodata/smodak/repos/f3rm/f3rm/feature_datamanager.py) still does image-batch fetch, pixel sampling, ray generation, whole-window cache stacking, and per-batch Python bookkeeping before the model forward. The baseline measure run also showed a repeat-window stall around the `512`-step resample boundary, so the next batch-side win is more likely in pixel sampling, ray generation, or window-stack churn than in the feature caches themselves.
- `P1` Shared feature/foreground trunk compression is the next invasive architecture idea in [feature_field.py](/robodata/smodak/repos/f3rm/f3rm/feature_field.py). The current field keeps separate hash encodings and separate MLPs for feature and foreground prediction. A shared TCNN-friendly trunk with slim heads could reduce `Timing/Train/model_forward` if it stays readable and quality holds.
- `P2` Keep import cleanup on the board, but only as a startup-overhead idea. [trainer.py](/robodata/smodak/repos/f3rm/f3rm/trainer.py) already skips viewer imports for non-viewer runs, and [extract_features_standalone.py](/robodata/smodak/repos/f3rm/f3rm/features/extract_features_standalone.py) already lazy-imports heavy extractors. If startup remains stubbornly high, inspect remaining non-viewer imports like GUI/PCA utilities before attempting larger refactors.
- `P2` Do not rewrite the SAM2/SAM3 async extraction orchestration unless startup profiling proves it still matters to cache-hit training. The benchmark uses precomputed features, so that code is more likely an import/startup problem than a steady-state train-step problem.

# Out Of Scope Issues For Human

- Build a repo utility that converts existing `features/foreground_` caches from float one-hot maps to compact uint8 label maps and rewrites any needed metadata, then run it across the scenes you care about. The runtime path already supports compact labels, but the repo does not yet give you a clean one-command migration workflow.
- Decide whether you want to invest in a CLIP-cache format project. The concrete work would be: choose an acceptable compressed representation, add a cache conversion or re-extraction path, and then run a fresh quality sweep to confirm the feature field still trains acceptably. That is a larger offline-data project than this contract pass should take on.
- Improve cold-start performance at the environment level if code-path startup cleanup is exhausted. Concretely: profile Python import startup in the container, trim unnecessary editable-install paths, and simplify the runtime image or environment so `ns-train` reaches the actual training loop faster.
- If you are willing to carry a local Nerfstudio fork, decide that explicitly and provide the policy for it. Then any unavoidable hot-path Nerfstudio changes can be staged under `nerfstudio_changes/` and copied manually, instead of being blocked by the no-site-packages-edit rule.
